- (event) Create intent confirmed; user wants interactive question-driven discovery. Source material found: model.puml (domain model: Project, Repository, Workspace, Worktree, Task, ChangeRequest, Agent, Session, SessionScope).
- (decision) Core concept: Workspace = tool for working with AI agents across a multi-repo (microservices) Project; per-ticket isolated Workspace with an orchestrator agent as main interface that checks out repos into git worktrees, decomposes work into per-repo subtasks delegated to agents, produces a stack of PRs, persists shared context/progress for all agents; multi-provider/multi-model per task.
- (event) Stakes: personal tool for the user's own work as a developer (not commercial). Brief purpose: first step of a disciplined spec chain (brief -> PRD -> UX -> architecture -> implement); user explicitly rejects vibe-coding after a prior prototype degraded into chaos over iterations. Rigor calibrated high on clarity/scope, low on market/business case.
- (assumption) Origin: user searched for existing tools and found none fitting the multi-repo + isolated workspace + multi-provider orchestration use case (specific tools not yet named).
- (event) Landscape research done, digest in addendum.md. Commodity: worktree per task, multiple CLIs, single-vendor subagents, single-repo stacked PRs (GitHub, Jul 2026). Not found: stacked PRs across repos, local a+b+c+d, persistent context per ticket across providers. Closest: Warp Oz, ivar.
- (event) Prior prototype failure modes: drifting concept model, losing track of what was implemented, regressions, performance problems, changing direction while the vision matured. Lesson: stable glossary, explicit v1 boundaries, spec as the source of truth.
- (event) Tools tested: Conductor, super.engineering (Shared Context, experimental, was closest but lacked several worktrees of the same repo in one workspace), Orca, others. Most add little over plain Codex/Claude Code. ivar and Warp Oz unknown to the user.
- (decision) Form factor: desktop app that can also run as a server, with continuation from mobile/browser. Agents talk to the app via CLI and/or MCP. Integrates the existing agent CLIs: Claude Code, OpenCode, Codex. Workspace drives them and does not call model APIs directly.
- (assumption) Several worktrees of the same repo inside one Workspace is a hard requirement. model.puml already allows it (Workspace 1-* Worktree, Worktree -> Branch).
- (event) Reference scenario: an 8 SP Jira ticket split into a 5-PR stack in the service repo, plus a GitOps infra repo and the BFF repo. Full journey in addendum.md.
- (decision) Workspace = a plain directory, not a git repo. The app seeds it with orchestrator AGENTS.md from a template and WORKSPACE.md describing the initiative. Artifacts like PLAN.md live there and are readable by all agents in the Workspace.
- (decision) Agent = profile (e.g. planner) binding provider + model + prompt. The orchestrator delegates to agents at Workspace scope (planner) and to workers at Worktree scope (implementers).
- (decision) Session scopes: Project (create/inspect worktrees), Workspace (orchestration/delegation), Worktree (implementation in one repo).
- (decision) Human-in-the-loop: the orchestrator/planner decomposes into Tasks, the user approves the plan before implementation, then work is delegated per worktree. The user sees progress in the GUI and can jump into any task to ask, request changes or pivot.
- (event) Today's workaround: Codex in the ChatGPT app, one project per workspace, skills that created worktrees. Worked but was chaotic. Pain points: the LLM spends effort on routine mechanics (creating worktrees, copying context); the GUI is not built for many workspaces over time (sidebar clutter); no dedicated UI.
- (decision) Orchestrators at two levels. Project orchestrator = intake only ('I am taking this ticket, create a Workspace'), nice-to-have, not v1. Workspace orchestrator = core of v1, organises the Workspace and creates its worktrees. Resolves the conflict over who creates worktrees.
- (decision) State model: runtime objects (Tasks etc.) are the source of truth for Workspace state, not markdown. PLAN.md = the planner's output, a companion file. The orchestrator turns it into Task objects. Only the orchestrator changes Task status. Workers report via handoffs to the orchestrator. The user is the approver.
- (decision) WORKSPACE.md dropped entirely. Its content (ticket, business context, constraints) moves to the runtime Workspace object as 'intent'. Reason: structured runtime state over markdown, even though the user likes ALLCAPS.md files.
- (decision) ChangeRequest = generic name for a GitHub PR / GitLab MR. Workspace must handle rebasing the CR stack automatically, route review comments back to workers automatically, and know the merge order across repos and show it. The user does the final merge themselves; Workspace tells them what goes to master and in which order.
- (decision) Workspace lifecycle: a 'completed' status that is not terminal (green badge, can reopen), and archiving to keep the list clean.
- (assumption) Who creates CRs is still open. Recommendation being proposed: workers deliver a branch + handoff; the orchestrator decides; creating CRs and rebasing are deterministic operations of the app, not LLM work.
- (decision) Principle accepted: deterministic operations belong to the app, judgment belongs to agents. Workers deliver branch + handoff, the orchestrator decides.
- (override) v1 exception to that principle: CRs are opened by the LLM agent with whatever forge tooling (CLI/MCP) the user installs, not by app mechanics. Keeps v1 forge-agnostic and simpler.
- (decision) v1 scope IN: desktop app; CLI/MCP for agent<->app; Claude Code + OpenCode integration; Workspace-scoped sessions; Tasks with dependencies; several worktrees per repo; CRs (agent-created, forge-agnostic); merge order across repos.
- (decision) v1 scope OUT: Codex CLI (its models are reachable via OpenCode); server mode / mobile / browser; Project orchestrator (intake); issue tracker integration incl. Jira (user pastes the ticket or brings their own MCP); git forge integration (GitLab at work, user installs their own CLI/MCP).
- (decision) 'Orchestrator' and 'planner' are the user's own role labels, not domain concepts. In the app they are just agents running in a Workspace-scoped session; an Agent = profile (name, prompt, provider/model).
- (decision) ChangeRequest = runtime object in the app, holding at most a link to GitLab/GitHub. The agent opens the CR with its own tooling, then registers it in Workspace via MCP/CLI (URL, repo, source/target, Task). The app computes merge order from Task dependencies.
- (decision) Moved to post-v1 on purpose: automatic CR stack rebase, routing review comments to workers, archiving. In v1 these are done by hand or by asking an agent in a session.
- (decision) Success criteria accepted: (1) the next real multi-repo ticket goes start to finish in Workspace without falling back to Codex/ChatGPT; (2) the GUI always shows what is done, in progress, and the merge order; (3) no copying context between agent sessions by hand.
- (event) First full brief draft written in Polish, with a glossary section and design principles. Open: completed status in v1 (assumption), handoff contents, purpose of Project-scope session in v1.
- (decision) 'completed' status is in v1. Only archiving moves to post-v1.
- (decision) v1 session scopes are Workspace and Worktree only. Project session scope is deferred.
- (decision) A worker's handoff contains: summary of changes, doubts, open questions, decisions needed, and references to the artifacts the worker produced.
- (change) Brief terminology: 'ticket' replaced with a generic 'work initiative / work description'. A ticket or issue is one form of it.
- (change) Brief reframed: plan-then-implement is only one example of a workflow, not the core. The core is the domain model (Project, Workspace, Task, Worktree/Branch, ChangeRequest, Agent, Session, Artifact). Users run Workspace-scope agents that can delegate to Worktree scope, or start Worktree sessions directly. Workflow is the user's choice.
- (decision) Artifact becomes a runtime object: the formalised result of an agent's work (e.g. a plan), replacing loose files. A model.puml change is proposed.
- (change) Glossary: Task = 'a unit of work in the Workspace' (no reference to a plan).
- (decision) No Artifact-Task relation for now.
- (decision) Handoff is its own entity, not an Artifact kind. It holds a summary, doubts, open questions and decisions needed, and references artifacts.
- (decision) Artifacts are versioned. A revised plan becomes a new version, not an overwrite.
- (decision) Handoff gets a 'verification' field (the user suggested 'checks'): evidence that the agent verified its work, i.e. what was checked and with what result.
- (change) model.puml updated: Workspace.intent/status, ChangeRequest.url, new Artifact, ArtifactVersion, Handoff and their relations (Workspace owns Artifact and Handoff; ArtifactVersion produced by Session; Handoff from Session, concerns Task 0..1, references ArtifactVersion).
- (decision) Handoff simplified to summary, verification, openQuestions. doubts and decisionsNeeded are folded into openQuestions (any doubt or decision can be phrased as a question). Marking an item as blocking or needing the user's decision is a PRD detail.
