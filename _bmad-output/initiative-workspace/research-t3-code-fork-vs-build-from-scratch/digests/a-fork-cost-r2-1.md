# Plug-in fork merge cost — round 2

Summary: Over the last 30 days upstream T3 Code landed 1,542 commits (about 51 a day). Since the orchestrator rewrite on 2026-10-02 it landed 841 commits in about 10 days (about 80 a day). All counts are `git log` on the local clone at 0e7346c. Almost every file a plug-in fork would hook into changed at least weekly, and the central ones changed daily. `ws.ts` had 81 commits in 30 days and two near-total rewrites (10-02, 10-06). `Sidebar.tsx` had 60. `ClaudeAdapterV2.ts` had 41 commits in its 10 days of existence. Real forks show the plug-in shape keeps the footprint in upstream files small: travisjneuman touches 86 upstream files for about 186 changed lines, against 182 fork-only files. Keeping it current still meant many sync merges, though. travisjneuman made 48 in 30 days, mostly 2026-10-03..10-12, run by an automated agent-driven "merge + fix build" pipeline. TrogonStack opened 20 sync PRs in 30 days. When the orchestrator was rewritten, TrogonStack dropped several fork features instead of porting them. Migrations have a clean escape hatch: Effect's `Migrator.make` accepts a `table` option, and TrogonStack ran a second ledger for 2 months. Hours spent per week are not observable from public data.

## Migrations

- **Runner.** `repo:apps/server/src/persistence/Migrations.ts@0e7346c` imports every migration statically into `migrationEntries` (ids 1–61). It then calls `Migrator.make({})` with `Migrator.fromRecord`, which uses the default ledger table `effect_sql_migrations`.
- **What `runMigrations` does.** It runs `reconcileV2PreviewMigration()`, then the migrator. Afterwards it logs a warning for any recorded id whose name differs from the manifest (lines 202–225).
- **Where it is called.** The only call site is `layerSetup` in `repo:apps/server/src/persistence/Sqlite.ts@0e7346c:25`. That file had 1 commit in 90 days.
- **No second migration set upstream.** Upstream has nothing for running a second migration set. The upstream doc (`repo:docs/internals/legacy-orchestration-migration.md@0e7346c` lines 44–52) explains why: the migrator compares ids only, so "There is no safe id range for a fork inside this ledger … fork schema changes belong in a separate migration table or outside the migrator entirely."
- **The mechanism exists in Effect.** The vendored Effect source `repo:.repos/effect-smol/packages/effect/src/sql/Migrator.ts@0e7346c:32-34` shows that `Migrator.make` options include `readonly table?: string`. The workspace catalog pins `effect: 4.0.2` (pnpm-workspace.yaml:56). I did not verify that the vendored copy is exactly 4.0.2.
  - A fork can therefore run its own `Migrator.make({ table: "fork_sql_migrations" })` on the same `SqlClient`, with a one-line hook in `Sqlite.ts` `layerSetup`.
- **Precedent.** TrogonStack PR #13 (2026-07-31), "move fork-only schema onto its own migration ledger", did exactly this. It notes that reserving ids ≥1000 "was a latent bug". TrogonStack later dropped the ledger in PR #71, once it had no fork schema left.
- **Caveat: the DB file can change.** The V2 rewrite switched the DB file to `statev2.sqlite` (`repo:apps/server/src/config.ts@0e7346c:144`). `initializeV2Database` copies `state.sqlite` once if `statev2.sqlite` does not exist. Upstream may switch the DB file again in a future rewrite. A separate fork-owned SQLite file avoids that coupling, at the cost of losing cross-DB foreign keys and transactions.

## Real fork sync cost

**travisjneuman/t3code** ("ndev.t3code")
- **Divergence.** `gh api repos/pingdotgg/t3code/compare/main...travisjneuman:t3code:main` shows 237 commits ahead and 0 behind.
- **Sync merges.** 77 "merge upstream" merges since 2026-08-27, 48 of them since 2026-09-12. Fork commits stop between 09-01 and 10-03; after that the fork merged several times a day (up to ~10 merges/day on 10-07 and 10-11).
- **Footprint.**
  - 182 added (fork-only) files.
  - 86 modified upstream files totalling about 186 lines added+deleted. Top ones: OrchestratorMcpService +17/-2, CodexAdapterV2 +17/-1, runtimeLayer +14, ClaudeAdapterV2 +13/-1, ws.ts +2, RpcAuthorization +2, AppRoot +3.
- **Sync breakage (non-merge commits clearly tied to sync, 30d):**
  - "restore imports and APIs lost in the nightly merge" (10-03), plus same-day "export getDesktopOrigin again" and "fork error classes use Schema.TaggedError".
  - "refactor(fork): move fork features behind Fork add-on hooks" (10-07).
  - "source updates build again after upstream's provider-core move" (10-09).
  - "build upstream nightly …2886" (10-09) and "…2908" (10-10).
  - "source updates no longer fail on upstream's rolling tags" (10-11).
  - That is about 6–8 fix commits against 48 merges. Two merge messages record conflicts: `orchestration-v2/Orchestrator.ts` and `packages/shared/package.json`.
  - One merge (10-07) notes "Restore upstream text in files where the fork only renamed things".
- **Automation.** The fork built itself an automated sync: "update button merges the newest upstream nightly", "updates resolve conflicts and build breaks automatically", "check for new upstream nightlies every 30 minutes".
- **`docs/internals/fork-add-ons.md`:**
  - Fork code lives in fork-owned files.
  - Upstream files get one-line hooks, each tagged `Fork add-on`.
  - Before and after each merge the sync counts the marker lines per file. Files that lost markers go to a "merge agent" for re-apply; if markers are still missing, the merge is aborted.
  - Stated reason: "upstream rewrites the code around a hook, git takes upstream's version, and the hook disappears without a conflict."

- **Divergence.** 351 commits ahead and 3 behind (compare API).
- **Sync PRs.** 32 PRs titled "chore: sync with upstream pingdotgg/t3code main" between 2026-07-18 and 2026-10-12, found with the REST search API (the GraphQL `gh pr list` returned 502). Cadence: about 2 a week in July–September, rising to 12 in 2026-10-02..10-12. That is 20 in the last 30 days.

  - Small ones: #52 +310/-201, 9 files; #72 +601/-227, 14 files
- **Ledger of divergences.** The PR bodies track numbered divergences (up to about 0027). Each sync retires the ones upstream has absorbed (0007, 0009, 0015, 0016, 0019, 0023, 0027 …).
- **What the rewrite cost (#71).** The fork dropped its native subagent threads (0003), its separate migration chain (0006), background work details (0011), the ACP prompt-stall watchdog, RPC trace joining and a dev browser marker, "because they conflicted with upstream's rewritten runtime". It did not port them.
- **Who does the work.** One maintainer (yordis) authors and merges the PRs.

**munimtechnologies/mtcode**: 1,492 commits ahead and 6 behind. 59 upstream-sync merges between 09-17 and 10-12, with messages like "merge origin/main: 112 upstream commits (… Effect 4.0.2 …)" and batch sizes of 2–112 upstream commits.

**patroza/t3code**: the default branch is `fork/dev`, 88 commits ahead and 6 behind. Not analysed further.

**Cost per week:** in practice, active forks sync about 2–30 times a week; 5+ a week has been typical since 10-02. Each sync carries 50–600 upstream commits, and every rewrite brings a feature-drop or re-port decision. Hours are not observable. Both well-maintained forks lean on automation or agents to make that cadence possible.
