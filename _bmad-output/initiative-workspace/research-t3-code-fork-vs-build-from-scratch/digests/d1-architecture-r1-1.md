# D1 architecture — round 1

T3 Code (pingdotgg/t3code, MIT, clone HEAD 0e7346c, 2026-10-12) is a large TypeScript monorepo (pnpm + Vite+), written throughout in Effect-TS v4 (`effect` 4.0.2, patched). It has one Node server (`t3` npm bin) that owns everything that runs: provider processes, git, terminals, and SQLite. Web (React/Vite), desktop (Electron 44), and mobile (Expo/React Native) are thin clients that talk to it over typed Effect RPC on a WebSocket at `/ws`. The desktop app starts the server as a child process (the Electron binary run as Node) and loads the web UI through a custom `t3code://` protocol. The server is event-sourced ("orchestration v2"). A pure orchestrator turns commands into events. EventSink commits the events, projections, command receipts, and outbox effects in a single SQLite transaction. An effect worker then runs provider and git side effects. Providers sit behind a driver/instance layer (settings, status, installation) and a `ProviderAdapterV2` runtime interface defined in `packages/provider-core`. The transport differs per provider: Claude uses the Claude Agent SDK, Codex uses `codex app-server` JSON-RPC over stdio, OpenCode uses a spawned `opencode serve` plus its SDK, Cursor uses `@cursor/sdk`, Muse uses `@muse-code/sdk`, Pi uses `pi --mode rpc`, Grok and Antigravity are flavors of a shared ACP adapter, and the generic ACP Registry adapter covers other agents. The data model is strictly single-root. A Project is one `workspaceRoot` directory. A Thread belongs to exactly one project and has at most one `worktreePath`/`branch`. The agent's cwd is `thread.worktreePath ?? project.workspaceRoot`. I found no first-class concept of a thread or project spanning several repos. The only multi-repo touchpoints are UI grouping of projects by repository identity, cross-repo PR links, and the orchestrator MCP that lets an agent create or drive threads in other projects.

## Leads

- How hard would it be to make a Thread multi-root (several repos, several worktrees)? `worktreePath` is threaded through Orchestrator.ts (5+ sites), ProjectionStore, ProviderSwitchService, checkpointing/Utils.ts, terminals (`contracts/terminal.ts`), and worktreeMcp. Checkpoints are per-cwd git refs. Next step: count the touchpoints and test whether a "project group" or an orchestrator-MCP parent thread could serve as a multi-repo coordinator without schema changes.
- The orchestrator MCP (claim 23) may already cover cross-repo orchestration. One parent agent could spawn threads in several projects. Check whether `createThread` accepts any `projectId` and whether it can launch with a worktree strategy (`packages/contracts/src/orchestratorMcp.ts`, `worktreeMcp.ts`, `apps/server/src/mcp/WorktreeMcpService.ts`).
- `t3.json` (`t3ProjectFile.ts`): per-repo setup scripts for worktrees. Check whether it is relevant for multi-repo bootstrapping.
- How Muse's V2 adapter is wired (claim 22), and whether the adapter registry is open to third-party or plugin providers (it is a static array).
- Upstream churn for a fork: 5,424 commits in about 8 months, a V1→V2 orchestration rewrite (`legacy/` importer), and very large core files. D-other should quantify merge-conflict risk (commit rate on Orchestrator.ts, contracts).
- Whether the web/desktop UI can run without the mobile, relay, and Clerk auth surfaces (stripping cost), e.g. `@clerk/*` in the catalog, `infra/relay`.
- `docs/internals/effect-services.md`, `remote.md`, `environment-auth.md`, and `docs/orchestration-v2/provider-capability-system.md` are not yet read.

## Looked for, not found

- No first-class multi-repo entity: no project with multiple roots, no thread with multiple worktrees or cwds, and no "workspace" grouping several repos in contracts. Grep for "multi-repo", "multiple repositor", and "cross-repositor" in docs found only PR-link context.
- No Tauri. The desktop shell is Electron only.
- No user-configurable extra directories per thread. `additionalDirectories` appears only for attachments and cwd (Claude, Antigravity) and in the ACP registry session listing schema.
- No plugin or dynamic provider loading found. Provider drivers are a static built-in array, and ACP Registry is the extension path for new agents.
- No database other than SQLite in the server (the `@effect/sql-pg` catalog entry is presumably for infra/relay; not verified).
