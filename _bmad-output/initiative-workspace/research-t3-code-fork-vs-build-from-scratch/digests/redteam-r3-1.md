# Red team — build-own vs fork

Status: COMPLETE (r3-1). ~25 tool calls; GitHub primary sources via read-only `gh`, plus 2 web searches.

## Strongest counter-argument
The from-scratch plan assumes T3 Code lacks the parts that are actually hard, but upstream already ships them or is building them. T3 Code already exposes an app-owned, thread-scoped `t3-code` MCP server to Claude, Codex and OpenCode sessions. Its toolkits cover orchestrator, project, thread, worktree and pullRequests, plus attachment and preview. Agents can already launch, list, read, send to, wait on and interrupt threads, delegate sub-agents across providers, link PRs to threads, and schedule recurring tasks. Its Orchestration V2 design (doc updated 2026-10-11) treats "provider switching and context handoff" and "explicit context handoff artifacts" as core concepts. A stacked plugin system is in review: npm-installed plugins in supervised processes, with tools exposed to agents over MCP, thread statuses, approval answering and palette/slash actions. Once that lands, the user's workspace, task and dependency layer could be a plugin instead of a fork. Two forks show the extension route working. what1f/t3kanban added a task-first board with Windows/macOS/Linux releases in about 10 days. munimtechnologies/mtcode is 1,492 commits ahead and only 6 behind, with one main maintainer merging upstream in batches. Meanwhile the PTY-first approach has measured, unfixed Windows/ConPTY failures (input truncation and splitting, lost Shift+Enter, orphaned `claude.exe` trees) and has no reliable session state. Its own users report spending "months battling detection bugs", and Anthropic closed the request for a state API as NOT_PLANNED. That leaves a solo after-hours developer rebuilding solved plumbing on the weakest integration surface, the same pattern as stalled from-scratch GUIs like opcode.

## Searched, found nothing
- No first-hand retrospective from a solo developer who built an agent orchestrator GUI from scratch and gave up or overran. The evidence for stalling is indirect (repo activity, deprecation notices). No time-to-build data either way.
- No documented case of a project migrating from PTY to SDK, or from SDK to PTY, with stated reasons. Nimbalyst runs both an Agent-SDK path and a CLI/PTY mode, and the CLI-mode bugs pile up, but I found no stated decision rationale.
- No evidence that T3 maintainers plan first-class multi-repo workspaces or task dependency graphs. Multi-repo requests are consolidated in #7041 with no commitment, and I found no dependency/DAG feature in issues or PRs. This weakens the "upstream will make it redundant" argument: upstream covers the MCP, handoff, PR and orchestration plumbing, not the workspace/task-dependency domain.
- No evidence of agents systematically ignoring app-provided MCP tools (as opposed to tools not loading). Not found.
- No ACP-specific evidence (e.g. OpenCode's ACP mode) beating PTY on Windows. Not searched in depth because of budget.
- The plugin system's merge timeline and maintainer acceptance are unknown. All the plugin PRs are open and stacked.
