# Red team — sidecar on T3

## Strongest counter-argument
The v1 plan makes its whole execution layer depend on a T3 Code surface that is six days old, pre-1.0 (0.0.x) and only in nightly builds. Outside-agent OAuth on `/mcp` merged on 2026-10-06 (#16336). The latest stable release, v0.0.45, shipped on 2026-10-02, so it predates the feature. Within days of the merge, OAuth clients reported that every tool call failed. The server accepts only one MCP protocol version (2025-06-18) and returned an empty 400 to clients that leave out the header (#16906, fixed 10-09; duplicates #17036 and #17649). The `t3_thread_launch` contract is still changing: it has no retry key, and `clientRequestId` (#16654) and mode limits for `/mcp` clients (#16653) are open PRs. The `t3code://` deep links the plan relies on did nothing on desktop from at least 0.0.38 until the bug was closed today (#9745). People bridging into T3 resorted to UI-automation hacks in the meantime.

The worse risk is data loss on Windows. T3's delete-thread dialog offers to remove *any* worktree path that a single thread uses. Unlike the automatic storage cleanup, that client code does not check whether the folder sits inside T3's managed worktree folder. Removal runs `git worktree remove --force`, and on Windows that follows directory junctions and deletes their targets (#14990, confirmed data loss, still open). So worktrees your own app creates and attaches with `existing_worktree` can be destroyed from T3's GUI.

The project's direction also points away from external sidecars. An in-process or supervised plugin system is in review (#16047-#16065). It covers run-finished events from an acknowledged cursor, plugin tools exposed over MCP, right-panel views and approvals. An earlier RFC (#6419) put the integration story as "your app renders inside T3", not "T3 is driven from outside". A sidecar built now targets the less-invested surface and must poll (`t3_thread_wait`) where plugins would get pushed events.

## Mitigating evidence found (fairness)
- Automatic storage cleanup keeps worktrees outside the managed folder, symlinked worktrees, and paths that contain a project checkout (`apps/server/src/storageCleanup.ts`). The automatic path is safe for external worktrees; only the manual delete dialog is the exposure.
- The protocol-version bug (#16906) was fixed within 2 days, and maintainers triage quickly.

## Searched, found nothing
- No explicit maintainer statement that the `/mcp` outside-agent API is unstable, experimental, or versioned. There is also no stability guarantee.
- No removal or rename of `t3_project_create` / `t3_thread_*` tools found; the changes found add fields (`clientRequestId`, mode limits).
- No reports from people running T3 alongside a second desktop app about two-app UX or ops costs beyond the deep-link workarounds in #9745 and the third-party gateway (boundsj/t3-fleet-gateway).
- No issue specifically about `existing_worktree` threads having externally created worktrees deleted (the risk is inferred from code and #14990).
